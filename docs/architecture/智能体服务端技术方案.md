# 智能体服务端技术方案：Deep Agents 运行内核

> 第二步设计稿，2026-10-23；开发验证记录更新于 2026-10-24。承接[后端与智能体服务端技术方案](后端与智能体服务端技术方案.md)中的对话、轮次、大纲、产物和事件契约。Deep Agents 0.7.32、HTTP/SSE、执行器和工作台已在独立项目落地；验证结果见[功能测试报告](../功能测试报告-20261025/功能测试报告.html)。以下保留原始设计意图，具体边界以当前代码及验收记录为准。

## 2. 单智能体装配方案

服务进程启动时创建**一个已编译的 Deep Agents agent**和持久化 checkpointer，在各轮复用；每次调用只传入本轮新消息与运行上下文。不同对话使用不同 `thread_id`，同一对话后续轮次使用同一个线程。不要每轮重新创建 agent，也不要把 UI 历史全文重复塞给已持久化的线程。[`create_deep_agent` 参数](https://docs.langchain.com/oss/python/deepagents/customization)

装配约束：

1. `model` 由新项目的 `model_config.py` 从本项目环境变量构造 OpenAI 兼容适配器；未配置密钥时服务仍可启动，但聊天入口返回 503。旧项目 `.env` 不会被新项目读取。
2. `checkpointer` 使用持久化 SQLite，连接由 FastAPI lifespan 管理；应用数据仍保存在独立的 `workspace.sqlite`，不能把 checkpoint 当作产物目录或前端消息库。[检查点的线程作用域](https://docs.langchain.com/oss/python/langgraph/persistence)
3. `backend` 使用线程作用域的虚拟文件空间：`/drafts/<turn_id>/` 存临时草稿；`/materials/`、`/artifacts/` 通过受限适配层投影当前对话可读的附件提取文本与产物源文件。默认 `StateBackend` 只适合线程内临时数据，不能自行提供应用数据库中的正式文件；实施时必须补齐投影、持久化和路径归属适配，不把宿主项目目录交给模型。正式产物只由 `publish_artifact` 发布。[Backend 说明](https://docs.langchain.com/oss/python/deepagents/backends)
4. `skills=None`、`memory=None`、不配置 MCP；项目根目录的 `agent.md` 只是开发规则，不能误传给产品智能体作为运行时记忆。
5. `subagents=[]`，并在生效的 `HarnessProfile` 中设 `GeneralPurposeSubagentProfile(enabled=False)`。仅传空列表仍会得到默认通用子智能体；启动验证必须断言模型可见工具中没有 `task`，也没有异步子智能体工具。[官方无子智能体配置](https://docs.langchain.com/oss/python/deepagents/subagents#running-without-subagents)
6. 当前模型可见工具固定为第 5 节的 10 个。显式排除 `delete`、`execute`、`task`、`write_todos` 和手动压缩工具；不加入 MCP、Skill 或其他检索/校验工具。用户确认的大纲和交付清单由应用数据库管理，任务行动进度由执行器投影。[框架工具配置](https://docs.langchain.com/oss/python/deepagents/tools)

建议的封装为 `AgentFactory`（装配）→ `TurnExecutor`（轮次生命周期）→ `ProductTools`（4 个产品工具）/`ScopedFileBackend`（文件投影与路径限制）→ `EventProjector`（框架事件映射产品 SSE）。框架可替换的参数集中在 factory，领域授权和数据写入留在应用层。`interrupt_on` 是对特定工具调用逐次审批的机制；这里的大纲卡片是跨两个 turn 的产品级确认，使用应用状态和确认接口实现，不给每次文件写入弹审批。[Deep Agents 人工审批机制](https://docs.langchain.com/oss/python/deepagents/human-in-the-loop)

## 3. 一轮执行如何工作

```text
POST 用户消息
  → 会话服务原子创建用户消息、turn，锁定该对话的执行位
  → TurnExecutor 用 conversation_id 的 checkpoint 注入本轮消息
  → 单智能体自行讨论、追问、选择产品、规划或调用约定的 10 个工具
  → EventProjector 将公开文字、行动和文件就绪映射为持久化 SSE 事件
  → 写入类任务先按目标做确定性验收，再流式生成最终回复
  → 写 turn 终态，释放执行位
```

- **普通交流**：智能体可以直接流式回答，不必创建产品任务或调用工具；信息不足且影响行动时追问。
- **整套产物请求**：智能体读资料并提交大纲卡片，本轮结束；`package_status=outline_pending`。用户在卡片编辑并点击“确认并开始”后，服务端启动一个新 turn，把**已确认文本与交付清单**作为权威输入交给同一线程，才允许生成。
- **目标明确的局部创建/修改**：智能体选择相关产品和文件后直接执行，按影响范围校验；不进入大纲确认。文件夹查看状态不作为目标选择依据。
- **终止、失败或重启后继续**：用户发新消息触发新 turn。智能体从当前对话判断要继续哪个产品，读取已确认大纲、已完成清单和当前源文件；服务端在确认大纲仍有效且目标唯一后，为新 turn 授予同一大纲修订号下**剩余交付项**的写入权限，不要求用户重复点击确认。目标不唯一时先追问；补充材料或新要求实质改变评测范围、执行方案或交付清单时，先更新大纲并让用户重新确认。不能对旧执行流做盲目 `resume` 并重复工具调用。

新 turn 只追加本轮用户消息或大纲确认信息；应用数据库中的稳定 `message_id`、`turn_id` 与 checkpoint 的内部消息 ID 建立映射。服务端消息与产物索引是 UI 的依据，checkpointer 负责模型上下文。每个对话的工作线程固定，服务重启后从相同 checkpoint 继续后续轮次；若框架升级或异常使 checkpoint 无法读取，恢复路径以应用数据、已确认大纲和现有文件重建线程，不能丢掉已交付文件。恢复时是否需要重建内部 `thread_id`，在小规模验证中确定并同步修订上一份方案。

## 4. 自主决策与服务端授权

系统提示词只固定产品边界：评测设计而非声称已实测；事实、假设和资料来源分清；目标不明确时追问；整包必须先出大纲；普通讨论和明确修改可直接处理；正式文件通过 `publish_artifact` 发布。各文档的具体质量要求来自旧 prompt 的对应部分，按任务引用或用文件工具读取，避免每轮都注入整套长模板。

2026-10-29 新增需求澄清边界，业务规则位于 `src/evaluation_agent/prompts.py`，由运行时系统提示词引用，工具说明同步约束模式选择顺序。进入 `package_outline` 前先读取相关资料，判断对象与场景、输入输出与范围、评测目的与主要风险、正确性判断依据四项是否足够。关键缺口先以普通聊天追问，确需产品绑定才选 `discussion`；同一轮范围不可切换，不先进入大纲模式再追问。追问通常不超过三项，复用历史和已读资料；无标准答案但有复核依据可继续，用户明确授权初版时允许带假设的探索性大纲。普通介绍和明确修改、续做不重启完整访谈。

本轮只增强模型行为指引，未新增结构化就绪表或服务端语义硬校验；原有大纲格式、确认及发布授权继续执行。真实模型行为与受控流程检查分别记录在[需求澄清验收](../需求澄清验收-20261029/验收说明.md)。

智能体决定**要做什么**，服务端决定**允许写什么**：

- 用户消息开始时，turn 的写入范围为 `undecided`。智能体先结合消息、同一对话的历史、附件内容与产品索引判断意图和目标；可直接回答、追问，或通过 `select_evaluation` 提交结构化类型、目标产品、用户请求依据和具体文件范围。服务端校验归属、范围与用户请求的一致性后才登记本轮能力；模型提供的类型标签本身不构成写入授权。
- `package_outline` 只允许读资料和调用 `submit_outline`，不允许正式产物写入。首次 `package_generate` **只由大纲确认 HTTP 操作**创建，并绑定确认修订号和交付清单。用户之后明确要求继续未完成的同一任务时，智能体选择目标，服务端从持久化的确认记录中派生 `package_continue` 授权，只覆盖该修订号下尚未完成的交付项及必要的关联修订；模型不能自行声明已确认或凭文字扩大清单。
- `focused_create` 只允许创建用户**明确要求的有限产物**，登记该轮固定的文件类型/目标集合；`focused_edit` 只允许修改当前产品已登记的目标文件，必要的关联现有文件可一起修订。若用户请求的是完整评测方案/整套交付，或所列新文件已等价覆盖完整交付包，必须走 `package_outline`；不得把整包一次声明为若干 `focused_create`，也不得在同一轮逐步扩展成整包。服务端对声明的用户请求依据、目标集合及完整包覆盖情况做校验；不能可靠区分时不授予新文件写权限，由智能体追问。
- `focused_rename` 仅处理用户明确要求的文件名变更：一次选定同一产品的全部目标 ID，再用 `rename_artifacts` 提交完整映射；该范围没有内容发布权限。文件名请求不能通过 `focused_edit` 重写正文来替代。服务端校验目标集合、名称冲突、扩展名和归属，在同一 SQLite 事务中更新整批名称、旧名别名、审计与事件；取消登记先提交则整批拒绝，改名先提交则整批保留。正文、导出字节、内容版本、ID 和确认大纲不变。
- 目标文件或所属产品含糊时，`select_evaluation` 不授予写权限，智能体先追问；能够从用户话语和资料判断时直接选择或建立产品任务，不增设固定的人工确认。`select_evaluation` 在同一事务内建立/选定产品、绑定本轮附件并登记 turn 范围，避免只完成其中一半；重试按 turn 与附件 ID 幂等。文件夹浏览状态、模型给出的路径或其他对话的 ID 都不能成为授权依据。
- `write_file`、`edit_file` 只能修改本轮 `/drafts/<turn_id>/` 草稿；正式写入只经 `publish_artifact`。每次正式发布都重新检查 `conversation_id`、`turn_id`、目标产品、范围、确认修订号、允许的交付项和取消标志。提示词中的承诺不是写权限。整包范围即使模型跳过大纲也无法发布文件。

这是一层能力门槛，不是固定的“规划→执行→反思”业务图。模型可以对普通请求直接回答，也可以自主调用文件读取、草稿编辑和 4 个产品工具。服务端按用户请求与交付范围做可检查的拦截，但自然语言仍有边界情况，不能仅靠文件数量或关键词宣称语义判断绝对正确；含糊时不写入并追问，用真实用户表述和“整包伪装成局部创建”的反例做回归评测。

## 5. 智能体可调用工具与服务端行为

**当前完整模型可见工具集恰好 10 个：Deep Agents 内置文件工具 6 个，项目新增产品工具 4 个。**“工具”仅指注册给模型、由它选择调用的函数；上传、存储、转换、校验、取消和推送属于服务端行为，不计入 10 个。内置工具以固定版本实际注册名称为准，实施时断言可见清单与本表相同。[官方内置工具](https://docs.langchain.com/oss/python/deepagents/tools)

| 来源 | 模型可调用工具 | 作用与边界 |
| --- | --- | --- |
| Deep Agents 内置 | `ls`、`glob`、`grep`、`read_file` | 查看当前对话范围的 `/materials/` 附件提取文本、`/artifacts/` 当前产物源文件，以及本轮 `/drafts/`。读取长文档时按路径/片段分步获取；不得看到其他对话。 |
| Deep Agents 内置 | `write_file`、`edit_file` | 仅创建或修改 `/drafts/<turn_id>/` 中的 Markdown/CSV 草稿；写入草稿不会产生用户可见产物，也不授予正式发布权限。 |
| 项目新增 | `select_evaluation` | 选择或创建当前对话中的产品，绑定本轮附件，提交本轮意图、用户请求依据和有限目标范围；服务端原子校验并登记授权。普通交流无需调用。 |
| 项目新增 | `submit_outline` | 在整包规划轮次提交可编辑大纲全文和交付清单；服务端保存并发 `outline.ready`。确认按钮走用户 HTTP 请求，不是模型工具。 |
| 项目新增 | `publish_artifact` | 给出本轮草稿路径、产品/交付项或既有产物 ID；服务端核验授权、转换 DOCX/CSV、校验并原子发布，返回 `artifact_id`，发 `artifact.ready/updated`。 |
| 项目新增 | `rename_artifacts` | 一次提交授权范围内的 `artifact_id` 与新文件名映射；整批原子改名，保留正文/版本/ID，并记录旧名别名、独立审计和 `artifact.renamed`、`tool.progress`。 |

2026-10-27 根据用户要求新增元数据批量改名，工具集由原 9 个扩展为 10 个；未增加任意目录、Shell、子智能体或额外检索工具。

文件适配层必须把应用数据库中的产品索引、已确认大纲、需求结论、附件提取文本与正式产物源文件投影为**只读、带来源和稳定 ID**的当前对话路径；本轮未绑定附件放在可读的 `/materials/inbox/`，归属由 `select_evaluation` 决定。Word 原件由服务端解析成文本供 `read_file` 阅读，不能假定内置工具直接理解 DOCX。产物修订时，模型读取旧源并写新草稿，再调用 `publish_artifact` 更新对应 ID。路径限制在 backend 层执行，正式发布再按数据库 ID 复核；模型不能通过传入其他对话 ID 或绝对路径绕过隔离。`conversation_id`、`turn_id` 由运行时上下文注入，不接受模型提供的值。[自定义工具与运行时上下文](https://docs.langchain.com/oss/python/deepagents/context-engineering#runtime-context)

| 非模型工具：服务端行为 | 实施位置 |
| --- | --- |
| 上传与解析 Markdown/Word、持久化附件/消息/产品索引/文件源、准备只读文件投影 | FastAPI、应用服务与数据库 |
| 大纲卡片编辑/确认、轮次范围授权、跨对话隔离、幂等和路径校验 | HTTP 接口与领域服务 |
| Markdown→DOCX/CSV 转换、确定性校验、原子发布、交付清单和最终验收 | `publish_artifact` 背后的应用服务与 `TurnExecutor` |
| 流式事件投影与计时、取消、重启恢复、预览/下载 | `EventProjector`、`TurnExecutor` 与 HTTP/SSE 接口 |

旧 `update_plan`、`finalize_run`、`validate_scope`、`report_progress` 不注册为模型工具。已确认大纲、`deliverables` 和服务端最终验收分别承担用户可见计划、进度和完成判定；执行器验收后再由**同一个智能体**进行简短的最终回复调用。旧 CSV、占位符和文件存在性检查可复用为服务端校验，但“必须有完整计划且必须有文件”只能用于整包验收，不能用于问答轮次。

## 6. 上下文窗口与多产品对话

首版明确采用**应用工作窗口 128,000 tokens**，其中包含准备送入模型的输入及输出预留；单次模型回复最多 **8,192 tokens**。预计输入达到 **102,400 tokens（工作窗口的 80%）** 时触发框架摘要，摘要后保留最近 **16,000 tokens** 的原始消息。余下空间供回复、工具调用与估算偏差使用。这是产品运行预算，不是模型供应商宣称的物理上限；当前配置的 OpenRouter `deepseek/deepseek-v4-flash-0731` 页面标称约 1,048,576 tokens，但实际可用窗口应以所选路由和响应为准。[模型页面](https://openrouter.ai/deepseek/deepseek-v4-flash-0731)

默认按模型 profile 百分比触发的摘要阈值不适合直接套在约百万 token 的物理窗口上；装配时配置 `SummarizationMiddleware` 的绝对阈值 `trigger=("tokens", 102400)`、保留量 `keep=("tokens", 16000)`，并设模型输出上限 8,192。摘要中间件之后的预算守卫在每次公开模型调用前估算实际系统提示、工具 schema、消息和 8,192 token 回复预留；内部摘要模型也经单独代理预检提示和回复预留。超出 128,000 工作窗口时阻止调用，保留原始资料。估算使用 LangChain 的近似计数器，非供应商精确计费数；真正模型路由的物理窗口和计数偏差仍需上线前联调。若实际模型路由支持的总窗口不足 128,000，启动配置检查应报错并要求调整工作窗口。[框架摘要参数](https://reference.langchain.com/python/langchain/agents/middleware/summarization/SummarizationMiddleware) · [Deep Agents 上下文压缩](https://docs.langchain.com/oss/python/deepagents/context-engineering#context-compression)

Deep Agents 自带大工具结果卸载和历史摘要；线程虚拟文件不跨对话共享。仍须控制文件读取和工具输出：附件按段读取，`publish_artifact` 只回传 ID/摘要，避免把整套产物正文反复放进消息。首版不另写一套滑动窗口、摘要循环或跨线程长期记忆。

一个对话可同时讨论多个产品，模型摘要可能把它们压在同一上下文里；**产物归属不能依赖摘要**。每轮开始给智能体一个简短的产品索引和本轮附件引用，具体事实与文件通过 ID 查询应用数据库。智能体修改正文前必须读取目标产品的当前产物；仅改文件名直接使用当前索引，不读取或重写全文。原始用户消息、已确认大纲、附件提取文本与当前源文件始终可由应用层找回，即使模型工作记忆被压缩也不会丢失交付依据。当前消息中的未绑定附件可先读后归属：判断明确就建立/选定产品并绑定，判断不明就追问；无须用户在上传时手工选文件夹。

不启用 `memory=`（它用于加载 `AGENTS.md` 类静态记忆）或共享 `store=`；不启用 Skill。摘要过程生成的文本不显示在用户的聊天回复中。[摘要与过滤说明](https://docs.langchain.com/oss/python/deepagents/context-engineering#summarization)

2026-10-27 已增加上下文状态投影：`ObservableSummarizationMiddleware` 继承固定版本的摘要中间件，保留 `SummarizationMiddleware` 注册名以替换默认实例，避免双重压缩；在实际摘要操作外层记录开始、完成、失败和取消，不改动框架的压缩算法、阈值或摘要重试。模型调用前及回复完成后估算完整请求，压缩前后均可更新占用。事件通过运行时配置取得对话/轮次 ID，记录至应用事件库，实例本身不保存可跨对话混用的状态。输入框展示的是最近一次调用的估算，非供应商精确用量、未发送草稿预测或累计计费用量；首次运行前显示未知。真实模型生产窗口实量验证的原有边界仍然保留。

## 7. 流式事件、计时与正常完成回复

固定版本的 `astream_events(..., version="v3")` 已用假模型验证。执行器先 `await` 得到 `AsyncGraphRunStream`，再遍历其原始协议事件；只投影顶层 `model` 的公开文本增量。`run.messages` 也包含 Deep Agents 内部摘要模型调用，因此不能直接当作用户回复；原始事件上的 `lc_internal_call` / `lc_source` 用于过滤摘要。产品事件先写数据库，再通过 SSE 发送；v3 为 Beta，升级框架时必须重新验证过滤逻辑。[事件流接口](https://docs.langchain.com/oss/python/langchain/event-streaming) · [Deep Agents 流式输出](https://docs.langchain.com/oss/python/deepagents/streaming)

- 普通交流可将模型正文增量直接追加到本轮同一条公开回复。写入类任务的工作阶段主要展示 `tool.progress`、`plan.updated` 和文件就绪事件；模型 reasoning 内容、工具参数、摘要过程文本及内部验证反馈不进入聊天正文。若目标模型在工具调用消息中夹带正文，联调时确定投影过滤规则。
- 第一段公开文字到达后立即推送；后续极小增量可按短时间窗口合并后落库和推送，不按整句或整段缓存。应用 SQLite 开启 WAL 与忙等待，消息快照和增量事件保持同事务；合并窗口以真实联调的流畅度和写入负载决定。
- 计时从服务端 `turn.started_at` 开始，模型调用、读文件、转换和校验都计入；流式文字暂停时计时继续。只有最终 `turn.completed/cancelled/failed` 才定格 `duration_ms`。
- `publish_artifact` 发布成功后直接写应用事件并使预览可用；不等待模型整轮结束。写入类任务在工作调用结束后先由服务端验收；通过后，执行器内部阶段切到 `finalizing`、turn 仍为 `running`，并封闭写工具。随后用**同一智能体、同一对话线程**做一次只读收尾调用，流式给出完成摘要。服务端用实际 `artifact_id` 组装可点击交付清单，最后发 turn 终态。验收失败时先给智能体有界修订机会，仍失败则流式说明真实的未完成状态，不能先说“已完成”再宣告失败。
- SSE 断线只影响观看；运行任务不与浏览器连接生命周期绑定。事件先落库后推送，重连按游标回放，前端不模拟打字光标。

## 8. 真正终止与恢复

现有 FastAPI `BackgroundTasks` 没有为每个任务保留可取消执行句柄。新 `TurnExecutor` 在 FastAPI lifespan 中管理 `turn_id → asyncio.Task`，创建时与数据库 turn 关联；`POST cancel` 先持久化 `cancel_requested`，再取消对应 task。执行器等待模型流、工具调用与事件消费停止后写终态。Python task 取消是否能及时传到具体模型适配器，需要在固定版本下验证；超时或阻塞工具必须有边界，不能把“收到取消请求”当成“已停止”。

DOCX 转换、CSV 写入等同步步骤可以放在线程执行，但线程无法被 `asyncio.Task.cancel()` 立即杀死。它们只能写入临时位置。**取消请求登记与文件正式发布共用数据库串行化边界**：发布事务取得写锁后检查 turn 状态、切换文件版本、登记产物和事件；取消事务也取得写锁并登记 `cancel_requested`。发布先提交则文件视为已完成并保留；取消先提交则发布事务不得登记文件，临时结果丢弃。转换仍在途时保持 `cancel_requested`，待其退出或被可终止的隔离执行单元停止后才发 `turn.cancelled`、释放输入；不能把异步 task 已取消误当作阻塞线程已经停下。`turn.cancelled` 发出后不得再有来自该 turn 的文件事件。

2026-10-27 前端修复快照刷新期间的事件队列竞态：消费完待处理事件后再释放刷新状态，侧栏历史请求不再阻塞事件消费。终止 POST 后立即查快照；等待终态时每秒补查，最多 15 次，单请求沿用 15 秒超时。失败或轮询耗尽显示同步提示与重试；只有服务端快照确认终态才恢复输入。SSE 每次连接成功及页面返回前台均主动查快照，切换对话使旧响应失效。

服务重启时清点仍为 `running/cancel_requested` 的 turn，写 `interrupted` 并释放会话执行位。已完成产物保留；用户要求继续时启动新 turn，重新读取交付清单和文件。Deep Agents 文档说明取消/中断的未完成工具消息可由 `PatchToolCallsMiddleware` 修复，但不能据此假设任意中断点都可安全原地续跑；要用模拟模型分别验证模型流中、工具执行中和文件发布边界的 checkpoint 行为。[中断后的工具消息修复](https://docs.langchain.com/oss/python/deepagents/human-in-the-loop)

## 9. 质量、安全边界与开发顺序

执行器已设置轮次总时限和图递归上限；单工具超时尚未实现。领域工具做路径和 ID 归属校验、文件大小限制、DOCX/CSV 内容检查及原子发布；上传文件内容按资料处理，不当作系统指令。最终验收由服务端按本轮目标执行：问答要求有效回复，局部修改检查目标文件和显式引用，整包检查确认清单与实际文件及其显式本地引用。验收失败可在同一 turn 内给智能体一次有界的修订机会；仍失败则保存部分文件并标记不完整，不伪报完成。收尾调用仍计入同一 turn 的执行时长。这些确定性检查不代表跨文件语义质量验证。

## LangSmith 观测接入（2026-10-27）

已增加可选的 LangSmith 追踪：配置 `LANGSMITH_TRACING=true` 并填写本地密钥后，每个 `TurnExecutor` 轮次创建一个根 trace，内部 Deep Agents 执行、补交修订和最终回复都嵌套到同一根下。模型和工具使用框架原生追踪；元数据携带 `conversation_id`、`turn_id`、`thread_id`，根输出记录真实轮次状态及可见回复。服务停止时有界等待 SDK 上传队列。

本地 `.env` 默认关闭追踪；源码不保存密钥。支持新版 Agent + Local 环境寻址，也保留旧版项目寻址，二者不能混配。启动只检查配置，不发起远端账号操作。连接检查脚本仅发送固定测试文本，不调用模型；账号创建密钥和云端实际可见性仍需配置后联调。操作见 [LangSmith 接入指南](../LangSmith接入指南.md)。
