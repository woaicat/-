# 后端与智能体服务端重构技术方案

> 第一阶段设计：先确定服务端领域模型、状态边界和前端交互契约。Deep Agents 运行内核的设计见[智能体服务端技术方案](智能体服务端技术方案.md)。截至 2026-10-24，独立应用 SQLite、产物发布、`/api` HTTP 路由、SSE 回放、异步取消和正式对话前端均已落地；接口、浏览器与真实模型的验证见[功能测试报告](../功能测试报告-20261025/功能测试报告.html)。本文保留部分原始规划文字，具体实现以代码和验收记录为准。

## 1. 为什么先定数据和契约

现有后端以一次 `request_id` 生成任务为核心：`/generate-plan` 启动后台任务，`runs/events` 保存运行和事件，文件按请求目录保存，manifest 在全部生成后才建立。前端历史主要存在浏览器本地。现有 SSE 能回放任务事件，但没有稳定的对话消息、回复增量、大纲确认、文件逐个就绪和真实取消语义。直接把 runner 换成 Deep Agents，仍无法让新前端可靠消费这些状态。

本阶段先做服务端协议设计，不改现有运行入口。目标是让对话、轮次、产品评测任务、附件和产物各有稳定身份；让浏览器刷新、断线、任务中止与服务重启后的页面状态都能从服务端恢复。

## 2. 总体边界

```text
聊天前端
  │ HTTP：快照、消息、附件、大纲、终止、预览
  └ SSE：回复增量、行动进度、产物就绪、轮次结束
       ↓
FastAPI 会话服务 ── 应用数据与事件库 SQLite
  │       └── 管理归属、并发、授权、持久化和事件投影
  ↓
Deep Agents 单智能体 ── 持久化 checkpointer（每个对话一个 thread_id）
  │       └── 负责理解目标、追问、规划和工具选择
  ↓
受限文件工具与 4 个产品工具 ── 附件库、产物库、校验器
```

- **应用数据库是前端状态的依据**：消息正文、附件归属、待确认大纲、产物索引、任务状态与事件游标都在此持久化。Deep Agents 的 checkpointer 用于智能体跨轮续接，不直接充当聊天 UI 数据库。[LangGraph 持久化说明](https://docs.langchain.com/oss/python/langgraph/persistence)
- **一个对话对应一个当前 agent thread**：正常情况下以 `conversation_id` 作为 `thread_id`，映射保存在对话记录中；若异常损坏的检查点需要重建，仍以同一对话的应用数据恢复上下文并更新内部线程映射。一个对话可包含多个产品评测任务；产品归属由本轮聊天意图和资料决定，产物抽屉的文件夹选择只影响查看。
- **正式产物只由 `publish_artifact` 发布**：框架的 `write_file`、`edit_file` 只写本轮草稿，不能绕开归属校验直接成为用户可见文件。模型可见工具完整清单及上下文预算见[智能体服务端技术方案第 5、6 节](智能体服务端技术方案.md)。[Deep Agents backend 说明](https://docs.langchain.com/oss/python/deepagents/backends)
- **首版按本地单用户、单服务进程设计**：SQLite 和本地文件足够；通过数据库约束实现同一对话单轮运行。不为当前需求引入任务队列、分布式锁、MCP、Skill 或多智能体。若未来改成多进程，运行执行器和取消机制需另行升级。
- **前端事件继续用 SSE，用户操作用 HTTP**：当前产品只需要服务端单向推送，已有 SSE 回放基础；通过游标恢复连接。无需为了终止或大纲确认引入 WebSocket。

## 3. 身份、归属和持久化模型

| 对象 | 主键与核心字段 | 责任与约束 |
| --- | --- | --- |
| `conversations` | `conversation_id`、当前 `agent_thread_id`、标题、创建/更新时间 | 左侧历史列表的唯一来源；独立智能体线程。 |
| `evaluations` | `evaluation_id`、`conversation_id`、产品名称、`package_status` | 同一对话中的一项产品评测；文件夹按 ID 归属，名称仅用于展示。`package_status` 为 `not_requested / outline_pending / running / incomplete / completed`。 |
| `evaluation_notes` | `evaluation_id`、事实/假设/待确认项、来源消息或附件 | 保存可追溯的需求结论；不得把模型假设当成用户已确认事实。 |
| `turns` | `turn_id`、`conversation_id`、可空的 `evaluation_id`、触发消息/大纲、工作范围、可空的确认大纲修订号、状态、`started_at`、`ended_at`、`duration_ms` | 一次用户消息或大纲确认触发的一次智能体执行；写入范围由服务端登记，普通讨论也有 turn。 |
| `messages` | `message_id`、`conversation_id`、可空的 `turn_id`、角色、正文、状态、产物引用 | 聊天视图的持久化正文；同一条智能体回复从首个增量到完成保持同一 ID。 |
| `attachments` | `attachment_id`、`conversation_id`、可空的 `evaluation_id`、消息关联、文件元数据、保存路径 | 上传即归属对话；产品不明时暂不绑定产品，由智能体结合聊天判断或追问。原始上传文件只读。 |
| `outlines` | `outline_id`、`conversation_id`、`evaluation_id`、完整可编辑文本、修订号、状态、确认时间 | 整套产物的用户确认凭据；状态区分待确认、已确认、因实质变更待更新，确认时保存用户编辑后的完整文本。 |
| `deliverables` | `deliverable_id`、已确认大纲及修订号、产物名称/类型、完成状态、可空的 `artifact_id` | 从确认后的大纲归一化出的交付清单；继续任务时处理同一确认修订号下的未完成项及确需修复的已有文件。 |
| `artifact_aliases` | 对话/产品/旧文件名 → 稳定 `artifact_id` | 改名后应用内相对文件链接继续定位原产物，旧名不能被其他文件复用。 |
| `artifact_rename_batches` | `batch_id`、唯一 `turn_id`、产品、改名映射与时间 | 单独记录元数据改名审计；同轮相同映射重试幂等，不增加内容修订号。 |
| `artifacts` | `artifact_id`、`conversation_id`、`evaluation_id`、文件名、源文件/导出文件路径、内容修订号、就绪时间 | 一条记录对应一个用户可见文件；修改时 ID 不变，当前内容更新。Markdown/CSV 为可修改源，DOCX 为派生导出。 |
| `events` | 自增 `event_id`、`conversation_id`、`turn_id`、事件类型、JSON 载荷、时间 | 先持久化再推送的 SSE 日志；按对话和游标回放。 |

实现时建议新建 `storage/workspace.sqlite` 保存上述应用数据，checkpointer 使用独立存储；旧 `runs.sqlite` 和旧输出目录暂留只读。附件按 `conversation_id/attachment_id` 保存，正式产物按 `conversation_id/evaluation_id/artifact_id` 隔离保存，文件名不参与归属判断。所有读取、预览、下载和工具调用都核验资源所属对话与产品，禁止仅凭传入的文件名拼接路径。首版不启用跨线程共享记忆或跨对话检索。

### 三层状态不能混为一谈

- **轮次状态**：`running → completed / cancelled / failed / interrupted`；终止请求期间为 `cancel_requested`，只有执行真正停下才进入 `cancelled`。
- **整包状态**：产品任务尚未请求整包、等待大纲、生成中、部分完成、全部完成。普通讨论或单文件修改不改变整包完成度；局部修改失败/取消时另在回复区域和文件夹标出最近一次修改未完成，避免把已有文件版本误认成整轮修改已完成。
- **文件状态**：只有完成写入、导出和校验的文件才登记为可预览的当前产物。整包被终止时，已就绪文件仍可打开；“未完成的任务产物”是所属整包的标记，不表示文件损坏。

同一对话最多一个 `running/cancel_requested` turn。创建 turn 和占用对话执行位必须在一笔数据库事务内完成，冲突返回 `409` 和当前 `turn_id`；服务端拒绝运行中的新消息和附件，不做排队。不同对话仍各自隔离。需要资料归属判断时，智能体可在同一对话内读当前消息所附的未绑定材料、相关历史和产品索引；明确是新产品就建立 `evaluation_id`，明确是补充材料就关联已有产品，确实无法判断时先追问。正式产物写入必须绑定本轮已确定的产品。

## 4. 大纲确认和产物发布的强约束

### 整套产物的确认门槛

完整评测包请求先运行一个**只读规划轮次**。智能体可读材料、追问或产出大纲，不能在这一轮写正式产物。大纲在同一文本编辑区呈现，至少覆盖评测目标、指标、数据样本、执行方案选择的设计思路与交付清单。该轮结束后对话回到空闲，等待用户编辑卡片并点击“确认并开始”。

点击确认时，服务端原子保存**用户修改后的文本**、确认修订号和归一化交付清单，再启动新的生成 turn。生成工具凭服务端授予的已确认 `outline_id + revision` 才能发布整包产物；模型文字中的“已经确认”不能替代授权。普通讨论和目标明确的局部修改可直接执行，无须每轮确认。智能体负责结合用户话语、资料和上下文判断“整包、局部还是讨论”，可自主追问；服务端不盲信其类型标签：局部新建只能覆盖用户明确要求的有限文件，若请求或拟创建的文件集合相当于完整评测包，应转为只读规划轮次；无法可靠区分时先追问，暂不授予新文件写权限。此门槛不要求智能体每次行动都由用户审批。

例如，“先只做评测指标框架”属于局部创建；“把现有方案的阈值改掉，并同步样本与手册”属于局部修改；“根据这份文档设计一整套评测方案”和“把目标、指标、样本、执行手册都做出来”都应先出大纲。`submit_outline` 是智能体提交大纲数据的产品工具：后端保存并发出 `outline.ready`，前端才渲染可编辑卡片；卡片不是智能体直接操控的工具。用户点击卡片按钮后的确认由 HTTP 接口记录。

卡片保存使用修订号防止旧页面覆盖新内容。若大纲形成后又补充了会实质改变评测范围、执行方案或交付清单的资料/要求，旧大纲进入待更新状态；智能体更新大纲后再确认，避免根据过期方案生成。用户可在卡片中直接改完整文本；确认时将文本解析成内部交付清单，解析不出关键交付项时在卡片中提示修正，不启动生成。

### 文件逐个就绪与继续任务

产物生成或修改采用“写临时文件 → 完成源文件/导出文件校验 → 发布新的内部文件版本 → 在同一数据库事务中更新当前 `artifact_id` 指向并写 `artifact.ready/updated` 事件 → 向 SSE 广播”。这样事件到达时预览接口已能读到该文件。中途崩溃只留下未登记的临时文件或内部旧文件版本，重启后清理；旧版不提供给用户。对于同一个 Markdown 源与 DOCX 导出，应作为一次发布单元处理，避免只更新其中一个。

每完成一个交付项即更新 `deliverables`，抽屉立即显示对应文件。终止后已完成交付项保持 `ready`，整包状态置为 `incomplete`。用户之后说“继续剩余工作”时，智能体从对话中确定目标产品，读取已确认大纲、交付清单和当前产物；服务端在确认目标唯一、大纲修订仍有效后，从原确认记录为**新 turn**派生仅覆盖剩余交付项的 `package_continue` 写入范围，无须用户重复点击确认。智能体只补未完成项，必要时修订关联文件；不能把已完成文件当成不存在而从头生成。目标不唯一时先追问；若新资料/要求实质改变原大纲，先更新大纲并重新确认。完整通过验收后整包才变为 `completed`，回复中的可点击文件清单由产物索引提供，不依赖模型手写文件名。

新产物不能沿用现有默认 6 小时自动删除策略；保留时长由后续显式清理功能决定。旧任务输出保持原有兼容路径，迁移时不直接删除。

### 元数据批量改名（2026-10-27）

`focused_rename` 绑定同一产品的完整目标集合，`rename_artifacts` 一次提交所有 ID/新名称；校验扩展名、名称唯一、别名保留和归属后，与取消登记共用事务串行化边界。中途任何失败都回滚整批名称、别名、审计和事件。只更新 `artifacts.filename`，不重写源或导出、不增加内容版本、不改变稳定 ID/路径，也不修改已确认的大纲和交付项名称；后续续做/验收按 ID 和别名核对原确认。文件 API 仍按 ID 定位，下载返回新名称。

应用 schema 从 1 加法升级到 2，仅新增上述两表并保留旧记录与文件。快照新增 `artifact_aliases` 与本对话最新 `progress`（带 turn_id）；前端预览将同产品的原名链接解析至稳定 ID。原文件正文及离线导出的相对链接文本不自动改写，应用内兼容不代表离线文件链接已替换。

## 5. 前端需要的最小 HTTP 契约

已实现的本地 API 使用 `/api` 前缀，OpenAPI 可在 `/docs` 查看；下表省略前缀。

| 请求 | 返回/行为 |
| --- | --- |
| `POST /conversations`、`GET /conversations` | 创建对话；按最近活动列出服务端历史。 |
| `GET /conversations/{id}` | 一次性返回消息、当前 turn、待确认大纲、产品文件夹摘要、文件索引、`last_event_id` 和 `server_now`，用于首屏及刷新恢复。 |
| `POST /conversations/{id}/attachments` | 空闲时上传 Markdown/Word，携带上传幂等键并返回 `attachment_id`；暂未确定产品归属可以为空。运行中返回 `409`。 |
| `POST /conversations/{id}/messages` | 接受正文、附件 ID 和客户端幂等键；原子创建用户消息与 turn，返回两者稳定 ID。运行中返回 `409`。 |
| `PUT /conversations/{id}/outlines/{outline_id}` | 保存卡片内完整文本，校验预期修订号；更新后返回新修订号。 |
| `POST /conversations/{id}/outlines/{outline_id}/confirm` | 校验待确认状态和修订号，记录明确确认并启动生成 turn；重复点击按幂等键返回同一 turn。 |
| `POST /conversations/{id}/turns/{turn_id}/cancel` | 记录终止请求并要求执行器停止；返回当前状态。主动查询或 SSE 后的快照确认 `completed/cancelled/failed/interrupted` 终态后，输入区才重新启用。 |
| `GET /conversations/{id}/events?after=N` | SSE 回放同一对话中 `event_id > N` 的事件，再接实时事件；支持 `Last-Event-ID`。 |
| `GET /conversations/{id}/evaluations/{evaluation_id}/artifacts` | 返回该产品文件夹的当前文件，包含稳定 ID、名称、类型、修订号、预览地址。 |
| `GET /conversations/{id}/artifacts/{artifact_id}/preview`、`.../download` | 只读预览/下载当前版本；服务端校验对话、产品和路径归属。 |

API 路径和字段名称可在 OpenAPI 实施时统一，但上述身份和行为不应变。对于消息上传，先上传的附件保留在对话内的“待发送附件”状态；发消息时按 ID 关联，刷新页面也能找回。智能体可通过受限 `read_file` 读取该消息所附的未绑定材料，再依据聊天及内容判断产品；`select_evaluation` 在同一事务中建立或选定产品、绑定这些附件并登记本轮工作范围，避免只完成部分操作。只有归属确实不明时才追问，工具不得静默把已经属于另一产品的附件改绑。用户不需要先在界面选择产品文件夹，文件夹查看状态也不推断目标。用户发“继续”仍使用 `POST .../messages`；服务端根据有效的已确认大纲派生续做权限，不新增一个要求再次点击确认的前端操作。所有写请求使用幂等键或修订号，避免断网重试产生两轮任务、重复文件或重复确认。

## 6. SSE 事件和恢复顺序

所有事件使用统一外壳：`v`、`event_id`、`conversation_id`、`turn_id`、`created_at`、`type`、`payload`。SSE 的 `id` 与 `event_id` 相同；客户端只按游标追加，忽略已应用事件。`message.delta` 额外包含稳定 `message_id` 与文字增量；不要等待整句或整段才发送，也不要额外模拟闪烁光标或人工打字。具体帧合并阈值在联调时按真实模型输出调整。[Deep Agents 流式输出文档](https://docs.langchain.com/oss/python/deepagents/streaming)

| 事件 | 前端动作 |
| --- | --- |
| `turn.started` | 建立本轮运行态，依据服务端 `started_at` 与 `server_now` 显示持续增长的“已处理”时长；禁用输入和上传。 |
| `message.started`、`message.delta`、`message.completed` | 对同一 `message_id` 追加正文，完成事件给出权威最终正文和可点击产物引用。 |
| `outline.ready`、`outline.updated` | 展示或更新可编辑大纲卡片；该规划 turn 随后结束，等待确认。 |
| `plan.updated`、`tool.progress` | 展示可理解的行动摘要与交付进度；不泄露模型内部推理或原始工具参数。 |
| `artifact.renamed` | 同事务整批落库后更新文件清单名称；ID/内容修订号不变。`tool.progress` 显示已完成改名数量。 |
| `artifact.ready`、`artifact.updated` | 立即把文件加入/更新到指定 `evaluation_id` 文件夹；使用 `artifact_id + content_revision` 刷新预览。 |
| `context.usage` | 更新当前对话的上下文估算：`used_tokens`、`window_tokens`、`summarize_at_tokens`、`max_output_tokens`、`estimated=true`、`basis`（模型请求或回复完成）。不暴露提示词、消息或摘要正文。 |
| `context.compression.started/completed/failed/cancelled` | 由框架真正执行摘要触发；开始时显示整理提示和转动圆环，完成后恢复工作提示，失败时说明可重试，取消后停止动画。计时和停止按钮沿用轮次机制。 |
| `turn.completed`、`turn.cancelled`、`turn.failed`、`turn.interrupted` | 该 turn 的最后一条业务事件；附 `started_at`、`ended_at`、`duration_ms` 和整包状态，停止计时并恢复输入。 |

事件写入应用数据库后才广播；消息快照与其增量事件在同一事务中更新。对话快照及 `last_event_id` 在同一读取事务中取得；客户端随后订阅大于该游标的事件，服务端先补历史再转实时。SSE 断开仅影响观看，不取消任务。刷新或重连后，已有正文来自快照，后续增量由游标衔接，不重复拼接；计时用服务端时间继续，结束后用 `duration_ms` 定格。终止事件必须在最后一条回复与产物事件之后，避免当前代码里 `finalize` 先于 `final_summary` 导致前端漏掉最终回复的顺序问题。

对话快照新增 `context`：包含窗口配置、最近一次 `usage` 和 `compression`（带 `turn_id` 与 `updated_at`）。旧对话没有统计时返回空值，前端显示“—”；不会将聊天记录长度冒充当前模型上下文长度。占用分母是应用窗口，输出预留另行列出；未发送草稿、尚未读取的附件不计入，回复正文完成后更新估算。统计按当前对话查询，晚到回调不得在轮次终态后追加事件；服务中断遗留的整理中状态按轮次终态显示为中断，不持续转动。上下文投影沿用事件表；后续批量改名的新增表见第 4 节。

可先定义版本 1 的事件 schema 并写协议测试，再把 Deep Agents 的模型/工具流转换成上述产品事件。当前官方 event streaming API 标为 Beta，接入前应固定依赖版本并验证其异步文本增量与工具事件行为；不能把框架原始事件直接透传给前端。[Deep Agents event streaming](https://docs.langchain.com/oss/python/deepagents/event-streaming)

前端快照刷新在当前视图内合并并发请求，循环消费刷新过程中到达的事件；退出刷新前不再等待侧栏历史请求，避免终态事件滞留。切换对话递增视图版本，旧响应和旧 SSE 不得覆盖当前状态。取消 POST 返回或失败后均主动查询状态；待终止期间每秒补查，最多 15 次，单请求 15 秒超时。状态查询失败或轮询耗尽时展示可重试提示，未确认终态前保持输入禁用。SSE `onopen` 与页面返回前台主动查询，终态或切换对话时清理轮询。

## 7. 取消、失败与重启

1. 手动终止先把 turn 置为 `cancel_requested`，通知运行中的智能体协作取消。取消状态登记与文件发布在应用数据库中串行化：发布先提交的文件保留；取消先提交时，发布必须检查到该状态并丢弃临时结果。执行器停止、在途转换退出或被可终止的隔离执行单元停止、文件发布完成或回滚并保存部分结果后，才写最终 `turn.cancelled`。取消请求到最终事件期间，输入和上传继续禁用；不能因异步 task 返回就推断阻塞工作已停止。
2. 取消时已发布的产物保留；未发布的临时文件不进入抽屉。后续继续任务是一个**新 turn**，读取已确认清单和当前文件，而不是重放整个旧 turn。
3. 异常失败保存已完成文件、部分回复和错误状态；可恢复的整包标记 `incomplete`。普通问答失败不凭空创建产品任务或文件。
4. 服务重启发现仍标记 `running/cancel_requested` 的 turn 时，登记 `interrupted` 终态并释放输入。是否可从框架检查点接续须在下一阶段验证；即使不能原地接续，也要能基于已发布文件启动新的“继续”轮次。
